# 场景数据保存格式

适用版本：Yun’s Scanner 1.0（build 13），2026-11-04。本文是场景 ZIP 的读取契约；采集实现与验证记录见 [采集与存储](采集与存储.md)，摄影测量与配准算法见 [数据处理](数据处理.md)。

## 1. 先区分两种导出

当前 Beta 单场景、批量保存均默认选择“重建结果”，也可以选择“原始归档”。读取时以 `scene-package.json` 的 `kind`、`schemaVersion` 和文件路径字段为准，不根据 ZIP 文件名猜测内容。

| 选择 | kind / schemaVersion | 用途与内容 |
| --- | --- | --- |
| 重建结果，默认 | `beta-reconstruction-scene` / `5` | 只包含通过筛选的图像、对应相机参数、可选深度及筛选报告；不包含完整视频、连续深度或未筛选点云 |
| 原始归档 | `beta-capture-scene` / `3` | 保留原视频、连续索引、全部原始关键帧及独立摄影测量输出，适合备份、诊断与重新处理 |

两种导出均新建 ZIP，不修改手机原场景。导出是否包含 LiDAR 与采集是否启用 LiDAR 是不同选项；导出不能补出从未采集的深度。摄影测量可能只返回部分图像的参数，新估计不会覆盖原始 ARKit 参数。

手机内部场景目录为 `Documents/beta-scenes/scan_*/`，ZIP 位于同级的 `exports/`。单场景 ZIP 内有一个场景目录；目录名可来自用户设置的场景名称。批量结构见第 7 节。

## 2. 默认重建结果包

以下结构对应 ARKit 实拍、摄影测量已成功配准的场景。文件名示例不表示实际帧 ID 连续。

```text
<场景目录>/
├── scene-package.json
├── selection.json
├── frames.jsonl
├── alignment.json
├── arkit/
│   └── poses.jsonl
├── realitykit/
│   ├── poses.jsonl
│   └── native-cameras.json
├── images/
│   └── frame_00002.jpg
├── depth/                         # 选择包含 LiDAR 时
│   ├── frame_00002_depth.bin
│   └── frame_00002_conf.bin
├── scene-info.json                # 可选
└── scene-location.json            # 可选
```

| 文件 | 格式 | 内容 |
| --- | --- | --- |
| `scene-package.json` | UTF-8 JSON 对象 | 包类型、版本、有效帧数、图像目录、默认相机文件、原始相机文件、帧清单、筛选报告、坐标及深度标定约定 |
| `images/*.jpg` | JPEG | 筛选通过的原始关键帧图像；不重编码、不旋转、不重新编号 |
| `arkit/poses.jsonl` | UTF-8 JSONL | 有效帧的原始 ARKit K/c2w，并附显式 GL/OpenCV w2c；保留原始曝光与质量字段 |
| `realitykit/poses.jsonl` | UTF-8 JSONL | 同一帧集合的 RealityKit 新内参及已配准外参；当前默认重建相机文件 |
| `realitykit/native-cameras.json` | UTF-8 JSON 数组 | 同一筛选 ID 集合的 RealityKit 原始返回值，未经轴转换或世界配准；K 对应估计尺寸 |
| `alignment.json` | UTF-8 JSON 对象 | 全局坐标/尺度变换、相机轴约定、拟合成员与差异统计；变换已经应用于 realitykit/poses.jsonl |
| `frames.jsonl` | UTF-8 JSONL | 有效帧 ID、时间、图像、原连续帧 ID，以及可选深度、置信度路径和尺寸 |
| `depth/*_depth.bin` | 小端 Float32 裸二进制 | 有效关键帧的原始米制深度图 |
| `depth/*_conf.bin` | UInt8 裸二进制 | 同帧深度置信度图 |
| `selection.json` | UTF-8 JSON 对象 | 接受 ID、排除 ID 与原因、原连续丢帧 ID、来源摘要、深度使用情况及配准记录 |
| `scene-info.json` | UTF-8 JSON，可选 | 用户设置的场景名称 |
| `scene-location.json` | UTF-8 JSON，可选 | 场景的 WGS84 经纬度、定位精度、时间和可用地址 |

JSONL 每一行是一个独立 JSON 对象，文件整体不是 JSON 数组。图片、两套相机和帧清单使用相同的有效 ID 集合，必须通过 `id` 与 `imageFile` 关联，不能按行号猜测。

### 2.1 总清单的读取入口

`scene-package.json` 的关键字段如下：

| 字段 | 类型 | ARKit 重建包中的含义 |
| --- | --- | --- |
| `schemaVersion` / `kind` | 整数 / 字符串 | `5` / `beta-reconstruction-scene` |
| `sceneID` / `frameCount` | 字符串 / 整数 | 原场景 ID / 筛选后图像数量 |
| `imagesDirectory` | 字符串 | `images` |
| `poseFile` | 字符串 | 默认 `realitykit/poses.jsonl` |
| `arkitPoseFile` | 字符串 | `arkit/poses.jsonl` |
| `realitykitPoseFile` / `realitykitNativeCameraFile` | 字符串 | `realitykit/poses.jsonl` / `realitykit/native-cameras.json` |
| `alignmentFile` / `pathBase` | 字符串 | `alignment.json`；路径以包内场景根目录为基准，所有相机的 imageFile 相对 imagesDirectory |
| `frameFile` / `selectionFile` | 字符串 | `frames.jsonl` / `selection.json` |
| `filteredFramesOnly` | 布尔 | `true` |
| `includesLiDAR` | 布尔 | 本 ZIP 是否包含深度和置信度文件 |
| `metricScale` | 布尔 | ARKit 实拍为 `true`；表示米制约定，不是测量精度认证 |
| `worldCoordinates` / `cameraConvention` | 字符串 | 原 ARKit 会话的米制、重力对齐世界；GL c2w 行主序，并提供两种 w2c |
| `videos` / `includesUnfilteredPointCloud` | 数组 / 布尔 | `[]` / `false` |
| `depthCalibration` | 字符串 | 原始深度应使用原 ARKit K 按深度尺寸缩放 |

### 2.2 有效帧清单

重建包的 `frames.jsonl` 与原始归档中的同名文件是不同结构。每行包含：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | 整数 | 原关键帧 ID，保留原编号 |
| `timestamp` | 数值 | 对应 ARFrame 的系统启动后秒数 |
| `imageFile` | 字符串 | `images/` 下的文件名，例如 `frame_00002.jpg` |
| `sourceFrameID` | 整数 | 原连续帧索引中的 `frameID`，不能视为关键帧 `id` |
| `depthFile` / `confidenceFile` | 可选字符串 | 相对场景目录的路径，例如 `depth/frame_00002_depth.bin` |
| `depthWidth` / `depthHeight` | 可选整数 | 深度与置信度图的宽、高 |
| `depthCalibrationPoseFile` | 可选字符串 | `arkit/poses.jsonl`，明确原始深度所用的标定来源 |

### 2.3 筛选报告

`selection.json` 的 `acceptedFrameIDs` 为最终有效名单；`excludedFrames` 是 `{id, reason}` 对象数组。当前排除原因包括：

| reason | 含义 |
| --- | --- |
| `quality_rejected` | 已有质量标记未通过 |
| `invalid_arkit_or_source_camera` | 原始相机矩阵或内参非法 |
| `missing_continuous_frame` | 缺少同时间连续帧记录 |
| `video_frame_dropped` | 对应连续视频帧未写入或有丢帧原因 |
| `tracking_not_normal` | 对应 ARKit 追踪状态不是 normal |
| `photogrammetry_missing` | 缺少可用摄影测量相机结果 |
| `alignment_rejected` | 仅兼容 v1 旧估计中已被配准删除的相机；v2 不以拟合排除名单剔除帧 |
| `camera_correspondence_invalid` | 图像、时间、原始内参或连续记录对应关系不一致 |
| `image_missing_or_invalid` | 图片缺失、无法解码、方向或尺寸不符 |
| `depth_missing_or_invalid` | 要求包含 LiDAR 时，同帧深度/置信度缺失、非法或与连续深度不一致 |

每帧记录首个命中的排除原因。`droppedContinuousFrameIDs` 仅作审计，不代表这些 ID 属于关键帧编号体系。`sourceFileSHA256` 引用导出前源场景中的文件；它们不必出现在筛选后的重建包中。`sourceAlignment` 保留原估计的配准统计，不是在最终帧子集上重新计算的误差，也不应再次作用到已对齐相机上。

有效帧数量为零、估计失败、源摘要过期、关键对应关系损坏等情况会拒绝导出重建结果。此时可以保存原始归档用于检查，程序不会静默替换成未经筛选的数据。

### 2.4 两套相机的共同坐标

ARKit 参数保持采集值；RealityKit 使用一个全局相似变换：`p_world = s * R * p_native + t`。相机中心按此式转换，相机旋转仅左乘 R，不能把尺度乘入旋转矩阵。相机局部轴转换由 `coordinateAdaptation` 声明；内参不受世界变换影响，只按估计图像与原图尺寸换算。默认 `poseFile` 指向 RealityKit，这是输出偏好，不代表精度排名。预览和现有训练仍使用原始 ARKit 输入。

`alignment.json.result` 保存 `scale`、行主序 3×3 `rotationRowMajor`、`translationMeters`、`inlierIDs`、`rejectedIDs`、位置中位数/P90、方向中位数及参考轨迹半径。原点和尺度参考都是本次 ARKit 会话，不是 GPS 或独立测量真值。`transformAlreadyApplied=true` 表示不能对 `realitykit/poses.jsonl` 再做一次配准；`native-cameras.json` 才是未变换的返回值。其 `sampleID` 对应其他文件的 `id`，列主序 K 对应同 ID 已对齐行的 `estimationWidth/Height`。

新估计报告 schemaVersion=2、alignmentPolicy=`global_similarity_fit_outliers_retained`。`inlierIDs/rejectedIDs` 只指参与/不参与稳健全局拟合的对应帧，不是相机精度判决；拟合未采用的有效相机仍以同一个全局变换输出。残差在全部源对应帧上统计，不仅是最终导出的子集。超过原 3 cm 等差异阈值只记录 `warnings`，不会单凭差值拒绝导出；缺少可辨识的全局变换、轴约定不明确或尺度退化仍会失败。两套参数保留局部差异，不逐帧贴合。

旧 v1 报告仍可导出已有结果，alignment.policy 明确标为 `legacy_inliers_only`，不会补造旧代码已删除的相机。重新估计后使用 v2 策略。完整原始帧继续保存在原始归档中。

## 3. 原始归档包

原始归档保存完整输入和独立结果。以下列表表示当前 ARKit Beta 流程可能生成的文件，深度、定位及成功估计结果均以实际存在和报告状态为准。

| 文件／路径 | 格式 | 内容 |
| --- | --- | --- |
| `color.mov`、`color-0001.mov` 等 | MOV，H.264 SDR 视频 | 连续拍摄视频；分段时产生多个文件，使用实际原生尺寸 |
| `images/frame_*.jpg` | JPEG | 全部已保存关键帧；不是视频每一帧都单独存成 JPEG |
| `poses.jsonl` | JSONL | 原始关键帧 ID、图像、时间、ARKit K/c2w、曝光时长、EV、ISO、质量信息及可选深度索引 |
| `frames.jsonl` | JSONL | 连续采集索引：`frameID`、时间、视频对应关系、原始 K/c2w、追踪状态、深度引用与丢帧标记 |
| `depth/frame_*_depth.bin` | 小端 Float32 | 关键帧原始深度，单位米 |
| `depth/frame_*_conf.bin` | UInt8 | 对应关键帧置信度 |
| `depth/continuous/*.f32` | 小端 Float32 | 连续采集的可用深度图，单位米 |
| `depth/continuous/*.u8` | UInt8 | 连续深度对应的置信度 |
| `review.ply` | 二进制小端 PLY | 采集彩色点云的有界预览副本，不是原始激光回波，也不是 3DGS 模型 |
| `review-poses.jsonl` | JSONL | 预览相机记录；当前 Beta 使用原始采集参数，不是 RealityKit 新估计 |
| `camera-estimation.json` | JSON | 当前摄影测量状态、有效/缺失 ID、深度输入 ID、来源 SHA-256、结果路径及配准记录 |
| `camera-estimation/<UUID>/cameras-realitykit.json` | JSON 数组 | RealityKit 原始相机结果；包含 `transformColumnMajor`、可选内参与畸变 |
| `camera-estimation/<UUID>/points-realitykit.ply` | 二进制小端 PLY | RealityKit 原始坐标系的彩色稀疏点云，尚未变换到 ARKit 世界 |
| `camera-estimation/<UUID>/cameras-arkit.jsonl` | JSONL | 新内参、原始内参和已对齐 ARKit 世界的 c2w/w2c；与重建包的 `realitykit/poses.jsonl` 来自同一结果，但尚未进行最终导出筛选 |
| `camera-estimation/<UUID>/points-arkit.json` | JSON 数组 | 已对齐米制点云；每项为 `position: [x,y,z]`、`rgb: [r,g,b]` |
| `capture-meta.json` | JSON | 设备/系统、实际格式、坐标/时间/深度约定、视频分段与流完成状态；旧包可能命名为 `meta.json` |
| `capture-processing.json` | JSON | 拍摄后处理状态、阶段、进度、模式与时间 |
| `capture-performance.json` | JSON | 采集性能诊断记录 |
| `beta-capture.json` | JSON | 拍摄时长、ARKit 估计路程、请求画质、原始收尾与相机估计请求标记 |
| `scan-summary.json` | JSON | 场景统计摘要 |
| `scene-package.json` | JSON | schemaVersion=3 总清单，`poseFile` 仍指向原始 `poses.jsonl`，新估计入口另在 `cameraEstimation` 中声明 |
| `scene-info.json` / `scene-location.json` | JSON，可选 | 名称 / WGS84 场景定位 |

原始连续索引中，只有 `videoWritten=true` 的记录对应已写入的视频样本；用 `videoFile` 和 `videoPTS` 找到具体视频帧，不按 JSONL 行号对应解码帧号。`timestamp` 是系统启动后的秒数，`videoPTS` 是对应视频段内的秒数；`timestamp - videoPTS` 可恢复该段时间偏移。参数索引可以保留未写入视频的丢帧记录。

build 12 起场景页为 ARKit 视频单独调整播放显示方向。该方向变换只存在于内存中的播放器轨道，包内 MOV/JPEG 仍采用 `capture-meta.json.imageOrientation` 声明的传感器像素方向，K 与深度仍对应这些原始像素。不得把场景页看到的竖屏尺寸或旋转再次套到包内相机参数上。

原始关键帧 `poses.jsonl` 中的 `depthFile`、`confidenceFile` 是 `depth/` 下的文件名；原连续 `frames.jsonl` 中的深度路径已经包含 `depth/continuous/`。这与第 2 节筛选清单的路径规则不同。

摄影测量重试保留独立 `<UUID>` 目录。只读取当前 `camera-estimation.json` 指向的结果：`estimated_aligned` 才提供有效米制相机入口；`alignment_rejected` 可以保留未配准的 RealityKit 原始输出，其余失败/取消状态不得解释为成功。不得仅通过扫描目录找到一个旧结果就视为当前结果。

原始归档关闭 LiDAR 时移除深度、置信度、相关索引字段及采集点云；已完成的独立摄影测量结果保留，并通过 `usedDepthInput` 声明估计时是否用过深度。清理后的 `poses.jsonl` 与估计时输入的摘要可能不同，总清单分别记录 `sourcePosesSHA256BeforeExport` 和 `exportedPosesSHA256`。原始归档不包含高斯训练工作目录或未发布的相机估计暂存目录。

## 4. 内参与外参的共同约定

### 4.1 内参

相机行中的 `intrinsics` 为对象：`fx`、`fy`、`cx`、`cy` 是像素单位数值，`width`、`height` 是对应图像的整数尺寸。针孔矩阵为：

```text
K = [ fx  0  cx
       0 fy  cy
       0  0   1 ]
```

使用每帧自身的内参，不假定自动对焦时所有帧相同。图像旋转、裁切或缩放后必须同步更新 K。已对齐估计文件中的 K 已从估计图像尺寸换算回原始 JPEG 尺寸，不能重复缩放。

估计相机记录还包含 `originalIntrinsics`、`estimationWidth`、`estimationHeight`，以及可选 `lensDistortionInEstimationPixels`。畸变数据仍属于估计图像像素坐标，当前流程没有因此执行图像去畸变。原 ARKit 记录没有保存畸变系数，不能把“未保存”当作“畸变为零”。

### 4.2 外参

`arkit/poses.jsonl`、`realitykit/poses.jsonl`、原 `poses.jsonl` 和已对齐的 `cameras-arkit.jsonl` 中，`transform` 均为 16 个数值组成的行主序 4×4 c2w：

```text
transform = [r00, r01, r02, tx,
             r10, r11, r12, ty,
             r20, r21, r22, tz,
               0,   0,   0,  1]
```

相机局部轴为 ARKit/OpenGL：X 向右、Y 向上、朝 −Z 看。ARKit 实拍的世界坐标重力对齐、+Y 向上、单位米；原点属于本次会话，不是 GPS 原点，不保证不同采集共享同一世界。

筛选后的两套相机和已对齐估计文件另提供：

```text
worldToCamera       = inverse(transform)
opencvWorldToCamera = diag(1, -1, -1, 1) × worldToCamera
```

二者也为行主序 4×4。OpenCV w2c 的前三行就是 `[R | t]`，相机局部轴为 X 右、Y 下、Z 前。c2w 的平移是世界中的相机中心，不能直接当作 w2c 的 `t`。

例外：RealityKit 原始诊断文件 `cameras-realitykit.json` 使用明确命名的 `transformColumnMajor` 和 `intrinsicsColumnMajor`，不能按上述行主序直接读取。重建使用总清单指向的已对齐相机，避免重复轴转换、相似变换或尺度归一化。

## 5. 深度与点云的二进制约定

深度和置信度文件均没有文件头，按图像逐行紧密排列，没有行尾填充。宽高来自对应帧记录，而不是 RGB 图像尺寸。

| 数据 | 每像素字节数 | 解释 |
| --- | --- | --- |
| 深度 `.bin` / `.f32` | 4 | IEEE 754 Float32，小端，单位米；非有限或非正值不可直接用于重建 |
| 置信度 `.bin` / `.u8` | 1 | UInt8：0=低、1=中、2=高 |

深度文件大小应为 `depthWidth × depthHeight × 4`，置信度为 `depthWidth × depthHeight`。重建包按帧筛选，但复制的深度像素保持原始值，读取时仍需过滤无效深度及低置信度像素。当前导出有效性要求至少约 1% 像素满足深度有限且大于零、置信度不低于中，并要求关键帧深度/置信度与同时间连续记录逐字节一致。

反投影原始深度时，使用原 ARKit K 按深度宽高缩放：`fx,cx` 乘深度宽/RGB 宽，`fy,cy` 乘深度高/RGB 高。不能无条件换成 RealityKit 新估计的 RGB K。深度是 ARKit `sceneDepth`，不是 LiDAR 原始激光回波。

PLY 文件头声明 `format binary_little_endian 1.0`；每点依次为 Float32 的 `x,y,z` 和 UInt8 的 `red,green,blue`，共 15 字节。`review.ply` 与 `points-realitykit.ply` 坐标来源不同，读取时需按第 3 节区分；它们不是包含协方差、透明度、球谐系数的高斯模型文件。

## 6. 普通视频导入的区别

普通视频没有同期 ARKit 位姿和 LiDAR，不能伪造另一套原始相机：

- 筛选重建包仍为 schemaVersion=5，但只有 `poses.jsonl` 一套摄影测量相机，`arkitPoseFile=null`、`metricScale=false`、`includesLiDAR=false`，世界坐标为归一化的任意尺度。
- 原始归档保留源视频、`images/`、`poses.jsonl`，以及 `video-source.json`、`video-frames.json`、`video-import.json` 等来源和处理记录。其 `photogrammetry-poses.json`、`photogrammetry-points.ply`、`points.ply` 分别保存原始估计相机、原始稀疏点云与归一化点云。
- 不将普通视频的时间戳伪称为 ARFrame 系统时钟，也不把归一化单位直接解释为米。具体处理契约见 [数据处理](数据处理.md)。

## 7. 批量 ZIP

```text
Scenes/
├── batch-manifest.json
├── <场景名称一>/
│   ├── scene-package.json
│   └── ...
└── <场景名称二>/
    ├── scene-package.json
    └── ...
```

`batch-manifest.json` 当前为 schemaVersion=2、kind=`beta-scene-batch`，`contents` 为 `reconstruction` 或 `original`；`scenes` 数组记录各场景 ID、名称、实际目录及是否包含 LiDAR。目录名会做安全处理和重名消歧，不改变内部帧 ID。批量任一场景导出失败则不发布该批 ZIP，不生成嵌套的场景 ZIP。

## 8. 读取顺序与实现入口

1. 先读 `scene-package.json`，确定导出类型、版本和尺度，按声明路径打开相机与帧清单。
2. 以 `id`、`imageFile`、`timestamp` 建立对应，核对图像尺寸和 K，不能用数组下标代替真实 ID。
3. 重建包只使用有效帧名单；原始归档需自行处理视频丢帧、追踪和估计缺失状态。
4. 需要深度时核对路径、宽高、字节数、置信度及标定来源；需要 OpenCV 时直接读取显式 w2c 或按第 4 节转换一次。
5. 米制配准残差只表示相对原 ARKit 轨迹的一致性，不能代替已知实物尺寸、独立重投影等精度验证。

源码入口：`Beta/BetaReconstructionExport.swift`、`Beta/BetaSceneArchive.swift`、`Capture/Models.swift`、`Capture/CaptureStreamRecorder.swift`、`Capture/CapturePhotogrammetry.swift`。它们均位于 `arkit-3dgs-scanner/` 下。

回归入口：`bash tools/test_beta_scene.sh` 检查两种归档、筛选与原始数据保护；`bash tools/test_capture_photogrammetry.sh` 检查相机/深度与坐标转换。`python3 tools/validate_capture_package.py <目录>` 用于含连续视频与 `capture-meta.json` 的原始 ARKit 归档，不能直接用于 schemaVersion=5 的筛选重建包。
