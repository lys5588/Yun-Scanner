# 数据处理

## 目的与输入输出

将普通手机视频转换为可追溯的训练图片、真实估计的相机和初始化点云。普通视频可走 Mac 页面或 iPhone 首页的“使用已有视频”。手机入口从照片或文件选择并在设备内完成处理，历史页另保留模型 ZIP 导入；App 内直接拍摄是另一条输入链路，拍摄前可选仅相机或相机 + LiDAR。直接拍摄的仅相机模式仍保留真实 ARKit 位姿，和需要重新估计所有相机的普通视频导入不同。

Mac 视频入口支持 MOV、MP4、M4V，要求 SDR、时长不超过 180 秒；检测到 PQ/HLG HDR 时拒绝处理。页面上传上限为 2 GB。每隔至少 0.5 秒选择一个原始解码帧，按比例缩小至长边不超过 1600 像素，不插帧或复制帧，至少需要 8 帧。

每次运行的数据位于 `local-data/runs/<实验编号>/scan/`：

| 文件 | 内容与用途 |
| --- | --- |
| `video-source.json` | 源文件名、SHA-256、ffprobe 探测信息、时间戳策略；明确没有 ARKit 位姿和 LiDAR 深度 |
| `images/frame_*.jpg` | 抽取并缩放后的图像，后续摄影测量和训练共用 |
| `video-frames.json` | `imageFile: String` 与 `timestamp: Double` 的有序数组；时间单位为秒 |
| `photogrammetry-poses.json` | 摄影测量返回的原始样本 ID、图像、时间、平移、四元数、列主序矩阵和可选内参 |
| `photogrammetry-points.ply` | 摄影测量的原始有色稀疏点云 |
| `poses.jsonl` | 每行一条兼容 `FrameRecord` 的训练记录，含图像名、源时间、行主序 c2w 和逐帧内参 |
| `points.ply` | 归一化后的有色初始化点云，不是高斯模型 |
| `video-import.json` | 相机约定选择、投影检查、归一化中心与尺度、有效/丢弃帧及原因、任意尺度声明 |

## 实现入口与约定

任务、上传、抽帧和状态管理由 `tools/mac_demo.py` 实现；`tools/prepare_video_scan.swift` 通过 `RealityKit.PhotogrammetrySession` 的 `.poses`、`.pointCloud` 请求获取实际结果；`Training/TrainingDataset.swift` 消费训练记录和点云，App 源码路径均以 `arkit-3dgs-scanner/` 为前缀。

手机入口由 `VideoImport/VideoImportView.swift`、`VideoImportCoordinator.swift`、`VideoFrameExtractor.swift`、`VideoPhotogrammetry.swift` 实现。使用 iOS 26+ 的实际 `PhotogrammetrySession.isSupported` 与设备输入上限，最多 200 帧、长边 1600、180 秒及 2 GB；不支持时允许预览但禁用准备按钮。抽帧通过压缩 sample 的 `CMSampleBufferGetOutputPresentationTimeStamp` 保留容器 edit-list 后的真实时间，精确取帧并核对 actualTime；应用一次 preferredTransform，通过 `forceSDR` 和 sRGB 色彩管理输出 8-bit JPEG，避免仅修改 HDR 标签。`video-frames.json` 还记录有理数时间、实际图像尺寸；`video-source.json` 保留 SHA-256、原始颜色、方向和处理方式。

`VideoPhotogrammetry` 用真实 `.poses` / `.pointCloud` 结果沿用下述几何契约；原始 lensDistortionData 保存在 raw poses 中，当前训练仍使用针孔近似，不声称已经做额外畸变校正。照片和文件源只读，App 处理私有副本。暂存阶段不出现在历史；取消需等待 RealityKit 结束，再删除本次暂存输出。最终 manifest 和概要完整后原子移动至扫描库，失败保留用户源视频。

**后台处理。** 准备任务由前台操作启动并申请持续后台时间。视频摄影测量使用 GPU，因此除了 iOS 26+ 接口，还必须同时通过设备后台 GPU 能力、签名 entitlement 和实际 `BGContinuedProcessingTask` grant 检查；仅提交请求不放行后台计算。未获准时切后台会安全停止当前准备，回前台可重新开始，原片不变；用户取消、系统到期、严重过热或内存警告仍可停止任务。抽帧/摄影测量没有断点恢复，不能承诺从停止的百分比续算。系统取消即使在前台也响应，强制结束 App 后不会继续。

build 8 将视频处理页的未获准提示明确为“正在前台处理，请保持 App 打开，完成后再切换”，避免将后台资源限制误认为前台计算启动失败。`VideoImportView` 只在实际 `.background` 时调用 `sceneDidEnterBackground()`；控制中心等引起的 `.inactive` 不再直接取消任务。真正切后台且无 grant 时仍取消并等待工作线程退出，保留所选原视频以便重新开始。系统到期、内存与温度保护保持有效；本改动没有增加后台 GPU 签名权限。诊断新增 `videoForegroundInactive` 和 `videoStoppedOnBackground`，用于区分短暂失焦与真实后台停止。

直接拍摄结束后的位姿优化和点云计算使用 CPU 持续后台申请，独立于视频摄影测量的 GPU 能力；实际授权不足同样走停止与数据保护。实时相机/ARKit 采集本身仍必须前台运行。共享生命周期入口为 `Background/ContinuedProcessingLease.swift`，任务结束前等待工作线程退出，避免双重执行或半成品发布。

当前 Personal Team 的 Background GPU Access 签名申请已被 Xcode 拒绝，因此默认个人版本仍需前台执行视频摄影测量，不能交付持续 GPU 后台准备。可选完整权限配置为 `Config/BackgroundGPU.entitlements`；具备签名权限后仍需实际设备能力与任务 grant，不能把此文件存在当作可运行证据。后台能力及任务事件在 `Documents/background-processing.json` 记录。

**时间戳。** 抽帧使用 FFmpeg `-copyts`、`-fps_mode passthrough` 和 `-avoid_negative_ts disabled`，保留解码后的源 PTS，不自动归零。起点可以非零或为负；时间必须有限且严格递增，图像数必须与时间戳数相等。这里的 PTS 是源视频的呈现时间，不是 ARFrame 系统启动时间，也不是拍摄的墙上时钟时间。

**相机与尺度。** 只有存在有效估计内参和位姿的帧才能进入训练，至少保留 8 帧，且图像分辨率必须一致。工具比较“返回矩阵直接作为 GL 风格 c2w”和“翻转局部 Y/Z 轴后作为 GL 风格 c2w”两种解释，通过点云的正深度和图像内投影计数选择；证据不足即失败，不补造相机。

归一化以原始点云均值为中心，以点到中心距离的第 95 百分位数的倒数为缩放因子；点云和相机平移应用相同变换，旋转与图像内参保持对应。`video-import.json` 写入 `metricScale: false` 和 `unit: arbitrary_photogrammetry_unit_normalized`，结果不能解释为米制。原始摄影测量结果另存，归一化不覆盖它们。

训练记录使用 GL/ARKit 相机轴约定（朝 −Z、Y 向上），不意味着该视频由 ARKit 采集。内参对应最终保存的 JPEG 像素。普通视频没有深度文件；曝光和 ISO 的零值仅为旧记录结构的兼容占位，清单明确标注未知，不能用于声称测得曝光或图像质量。Mac 训练入口关闭深度初始化、深度损失和再次位姿精修。

ARKit 采集路径的 RGB、内参、位姿和深度需关联同一帧，深度保留其原始分辨率与米制语义；普通视频不生成这些传感器数据。后续 COLMAP 导出由 `Capture/ExportManager.swift` 负责 GL c2w 到 OpenCV w2c 的转换；启用世界 Y/Z 翻转时同步变换位姿和点云，不能在输入侧重复翻转。训练或优化后的位姿另存，不覆盖原始采集记录。视频历史不提供 ARKit 米制优化和公尺量测，已旋正的 JPEG 预览不再按重力旋转。普通视频归档时 `points.ply` 保留任意单位；`training-coordinate-frame.json` 记录 `metricScale`、`unit`、`inputGravityAlignment`、`inputWorldToCOLMAPRowMajor` 和 `worldRotationMeaning`，明确 COLMAP 的可选世界旋转只是导出约定，不是重力或尺度校准。无效视频清单在覆盖旧输出前失败。

**LiDAR 与真实尺度（2026-11-03 代码核对）。** 实时拍摄的两种模式都使用 `ARWorldTrackingConfiguration`，ARKit 的视觉惯性追踪给出局部世界中的米制位姿；关闭本 App 的 LiDAR 深度采集不会把位姿改为任意尺度。米制表示单位约定，不保证无漂移或达到某一测量精度。Apple 的 [AR 坐标示例](https://developer.apple.com/documentation/arkit/providing-3d-virtual-content-with-scenekit) 和 [depthMap 定义](https://developer.apple.com/documentation/arkit/ardepthdata/depthmap) 分别说明位置和深度的米制含义。

拍摄前开启 LiDAR 会请求 `sceneDepth` 并保存深度与置信度；`PointCloudAccumulator.extract` 将 K 按深度图尺寸缩放、反投影，再通过同帧 c2w 放入 ARKit 世界坐标。深度点与相机因而在同一坐标和尺度约定下，但生成点云使用的正是该估计位姿，不能把点云自动当作独立的位姿真值。Beta 的 `configureBeta()` 关闭原自研位姿精修，停止后保存原始关键帧记录，再运行下述独立 RealityKit 估计；结果页 `BetaSceneView` 的“使用 LiDAR”仅控制点云显示和归档深度，不估计尺度因子、不执行点云配准或全局位姿优化。原始参数始终保留。

后续直接使用同一采集的 `images/`、逐帧 K 和 c2w 重建时，应保留米制坐标；若归一化，要记录并在导出时恢复变换。LiDAR 可作为深度约束和尺度检查依据，需由重建程序实际读取、滤除低置信度数据并计算残差。若重新运行纯视觉 SfM 得到另一个坐标系，需根据对应相机/三维点估计包含尺度的相似变换，并共同变换相机和重建点云；仅打开导出开关不完成这一步。普通视频没有同期 ARKit 或深度时，仍需要已知尺寸或可配准的米制参考。当前已核验的 49 关键帧场景无 LiDAR，不构成 LiDAR 尺度校正或精度验收。

**失败语义。** 抽帧不足、时间不合法、摄影测量缺失结果、非有限坐标、无效内参、分辨率不一致或相机约定不明确都会中止任务。日志保留在实验目录的 `run.log`。`video-import.json` 在训练输入准备完毕后写出；任务失败或取消不标为完成。准备完成但训练工具不可用时标为 `ready_for_training`，不代表已生成模型。

### Apple 相机估计与 LiDAR 优化能力核对（2026-11-03）

已对照 Apple 官方文档及本机 iPhoneOS SDK 的 `ARCamera.h`、`ARConfiguration.h`、`AVCameraCalibrationData.h` 和 `RealityFoundation.swiftinterface`，区分下列能力：

| 接口 | 已公开能力 | 对本项目的边界 |
| --- | --- | --- |
| `ARCamera.intrinsics/transform` | 读取当前帧 K 与 c2w | 只读；未发现向 ARKit 写回优化 K 或控制其内部 BA 的公开接口 |
| `AVCameraCalibrationData` | 读取可用内参、参考尺寸、畸变查找表及相机间标定 | 标定数据容器，不是估计器；其 extrinsicMatrix 相对参考相机、平移单位毫米，不能替换 ARKit 米制世界位姿；ARFrame 的 sceneDepth 不是 AVDepthData，不能假定能从中拿到该对象 |
| `PhotogrammetrySession.Request.poses` | 输出估计坐标系中的相机位姿 | iOS/macOS 26+ 的 Pose 另有可选 intrinsics 与 lensDistortionData；不保证比原始 ARKit 更准，也不承诺保留原世界坐标 |
| `PhotogrammetrySample.depthDataMap` | 给自建样本提供深度，帮助恢复实物尺度 | 可以设置深度；公开文档不保证按我们期望的损失函数精修 K/R/t |
| `ObjectCaptureSession` | 官方引导式拍摄及 LiDAR 数据路径 | 可作为单独对照；不等同于把既有 scanner 点云直接传给 PhotogrammetrySession |

来源：[ARCamera](https://developer.apple.com/documentation/arkit/arcamera)、[相机标定数据](https://developer.apple.com/documentation/avfoundation/avcameracalibrationdata)、[参考相机外参](https://developer.apple.com/documentation/avfoundation/avcameracalibrationdata/extrinsicmatrix)、[摄影测量位姿](https://developer.apple.com/documentation/realitykit/photogrammetrysession/pose)、[深度与尺度](https://developer.apple.com/documentation/realitykit/photogrammetrysample/depthdatamap)。Apple DTS 在[相关答复](https://developer.apple.com/forums/thread/840946)明确区分自建样本深度与 Object Capture 的 LiDAR 点云路径：没有直接传入点云的公开接口，也不能通过自建样本设置相机内参/位姿。本机 SDK 进一步确认 sample.camera 和 depthConfidenceMap 只有 getter，Camera 没有公开初始化器；depthDataMap 有 getter/setter。不能绕过这些限制声称官方提供了既有 ARKit 相机参数的联合优化入口。

项目已实现两条不同路径。`VideoImport/VideoPhotogrammetry.swift` 已读取官方估计的内参、位姿和可选畸变并保存原始结果，当前普通视频输出会归一化为任意尺度，不能直接复用于米制 ARKit 优化后覆盖原记录。`Capture/OfflinePoseRefinement.swift` 调用自研 `BundleAdjuster`，利用图像匹配重投影、LiDAR 深度及 ARKit 相对运动先验精修位姿；可选 `LocalSurfaceRefiner` 检查局部表面。它使用输入逐帧 K，未优化 fx/fy/cx/cy。保留特征匹配与独立照片对齐检查决定是否接受修正；Beta 不进入这条自研精修路径，改为下述独立 RealityKit 估计。代码中的历史精度描述不作为本轮真实数据验收。

本轮确定目标是单次采集内统一米制；建议先保留 ARKit K 作为基线，评估带有效深度的真实采集在位姿精修前后的留出重投影、深度一致性及已知实物长度误差，再决定是否需要内参修正。单独比较 K 是否恒定不能评价校准准确性；降低优化训练残差也不能代替独立精度验证。若后续增加内参优化，应使用受约束的低自由度修正与标定证据，避免 K、位姿和深度偏差相互补偿。优化结果、坐标变换和评价另存，原始参数保留；若采用官方重新估计路线，需验证并记录到原 ARKit 世界的配准与尺度变换。本轮尚未运行这些对比实验。

## Beta 的米制相机估计（2026-11-03）

入口为 `Capture/CapturePhotogrammetry.swift`、`CapturePhotogrammetrySamples.swift`、`MetricCameraAlignment.swift`。Beta 收尾后自动执行，预览页可重试。支持 iOS/macOS 26+ 且 RealityKit 能力检查通过的设备，至少 8 张、至多设备上限与 200 的较小值；超限明确报状态，不静默抽样。按需读取 JPEG，估计长边最多 1600 像素，不改写原图；不假造镜头 EXIF 或重用普通视频的任意尺度归一化。

1. 原始 `poses.jsonl` 提供图像 ID、真实时间、原始逐帧 K/c2w 与同帧深度索引。验证完成的 ARKit 流和 gravity 世界约定；导出中没有深度字段的历史 RGB 包仍可读取。
2. 读取米制 Float32 深度和可用置信度，屏蔽低于 medium 的像素及非有限/非正深度，最近邻扩展到实际估计图像尺寸，单位不变。有效深度不足 1% 时省略深度输入，并记录实际送入的 ID。该接口文档只说明深度辅助尺度，不能承诺执行几何深度残差优化；没有公开的任意 LiDAR 点云或 ARKit K/c2w 先验写入 API。官方解释见 [Apple DTS](https://developer.apple.com/forums/thread/840946)。
3. 请求 `.poses`、`.pointCloud`，用真实 sample ID 关联原图。返回的可选 K 缺失或非法时不补造；原始相机/畸变和点云先保存在独立结果目录。
4. 检查直接 GL 与局部 Y/Z 翻转两个相机约定。候选需有足够画内正深度点、可辨识的全局相似变换；两个候选都成立时先用方向残差相差超过 5° 的证据消歧，否则要求投影能分辨。世界旋转使用对应相机方向，尺度/平移使用相机中心；至少 8 个对应、ARKit 轨迹 RMS 半径至少 2 cm。最多四轮稳健拟合，拟合成员保留比例至少 80%。build 13 起，拟合外点也使用同一全局变换输出；不逐帧吸附到 ARKit。位置中位数 max(3 cm, 3% 半径)、P90 max(8 cm, 8% 半径)、方向中位数 5° 改为差异提示阈值，不再作为精度验收或整组拒绝条件。残差在全部对应帧计算。配准只建立共同坐标，ARKit 不是真值；几何退化或无可靠坐标变换仍会失败。
5. 同一个相似变换作用于相机中心和稀疏点，旋转矩阵不带尺度。导出行主序 ARKit/OpenGL c2w、其逆 w2c，以及局部轴翻转后的 OpenCV w2c。K 依估计尺寸换算回原图像素；畸变数据单独标明仍在估计图像像素坐标，未执行去畸变。原深度标定仍引用原始 K，不能把新 K 无条件替换进去。

| 文件 | 内容 |
| --- | --- |
| `camera-estimation.json` | 状态、方法、原始 poses SHA-256、输入/实际返回/接受帧数、缺失 ID、实际深度输入 ID、配准变换与残差、当前结果路径 |
| `camera-estimation/<UUID>/cameras-realitykit.json` | RealityKit 原始相机、可选内参与畸变，未经米制配准 |
| `camera-estimation/<UUID>/points-realitykit.ply` | 同次 RealityKit 原始稀疏点云，不能直接作为原 ARKit 世界点使用 |
| `camera-estimation/<UUID>/cameras-arkit.jsonl` | 仅接受帧的估计 K、原始 K、c2w、w2c、OpenCV w2c、图像/时间/估计尺寸 |
| `camera-estimation/<UUID>/points-arkit.json` | 同变换对齐后的米制点与颜色 |

只有 `estimated_aligned` 提供已对齐路径；`alignment_rejected` 保留原始 RealityKit 输出用于诊断；`unsupported`、`insufficient_frames`、`too_many_frames`、`failed`、`cancelled` 不伪造相机。失败不覆写采集参数，重试保留先前结果目录，当前报告只指向本次完成结果。中间目录不进入 ZIP，结果目录和报告分别原子发布，取消需排空 RealityKit。全局 gate 防止多个页面同时运行该估计。此阶段前台执行，临界温度或内存警告取消；手机资源行为仍需实测。

预览和训练输入暂时继续使用原始记录。Beta 默认“重建结果”ZIP 的 `scene-package.json.poseFile` 改为筛选后的 `realitykit/poses.jsonl`，`arkitPoseFile` 指向同一 ID 集合的 `arkit/poses.jsonl`。缺失估计、录像丢帧、跟踪异常、质量拒绝、无效图像或参数的帧不会混入；选择包含 LiDAR 时，还要求有效同帧深度/置信度。`frames.jsonl` 是该包的有效帧清单，与原始连续索引具有不同 schema；新包不作为旧 `capture-meta.json` 采集包解析。`selection.json` 保存来源摘要及剔除原因，移除深度文件仍如实声明估计曾使用深度。完整原始资料通过“原始归档”单独保存；未成功米制配准时拒绝导出重建结果，不回退为未经筛选的数据。

Mac 已用旧真机 49 张关键帧完成真实回放：45 个相机、5,043 个点通过配准，4 张没有输出；所有 59 个原始文件摘要不变，矩阵逆、相机轴转换、内参像素缩放、点云变换独立检查通过。位置差异中位数 2.69 cm / P90 3.71 cm、方向中位数 0.47°，约 16 秒。结果位于 `.build/metric-camera-replay-20261103-d/`，真实取消排空日志为 `.build/metric-camera-cancel.log`。样本无 LiDAR，不构成深度输入或绝对尺度/精度提升验收。
